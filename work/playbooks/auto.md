# Auto

For pursuing one goal the user states up front to completion. Auto wraps a sequence of playbooks: the goal splits into units, each unit runs on the playbook it matches, and you are the orchestrator. Fresh subagents run the units; you plan, brief, verify, trigger fresh reviewer subagents directly, and chain (Guard the Context Window). The deliverable is the goal's done condition met on evidence, or the handovers that only the user can pass. The run keeps going without check-ins: the next unit dispatches as soon as the last one is accepted (**[never-block-on-the-human](../principles/never-block-on-the-human.md)**).

1. **Fix the goal.** The goal in one sentence, a binary done condition, constraints and prohibitions, the environments in reach, and any session grant the user has given. Start the log with `--playbook auto` and log each of these as a note. Done when a command or an observation can check the done condition.
2. **Plan the units.** Split the goal into units, each with its playbook, its exit evidence, its scope (files, branch, targets), and the units it blocks. Size a unit so one fresh agent finishes it without compacting. Only units with disjoint scopes run in parallel (**[separate-before-serializing-shared-state](../principles/separate-before-serializing-shared-state.md)**). A `Deploy` unit splits at Deploy step 6 into preparation (steps 1–6 → orchestrator review) followed by execution (steps 7–9) continuing the same delegate log once `Decision: PASS` is reached. For a significant, complex, or high-risk multi-unit plan, the orchestrator may run a fresh reviewer subagent following [`review.md`](review.md) (`Mode: plan`) before dispatching units to catch architectural or sequencing defects early. Log the plan as a note and post it in the reply, then dispatch without waiting: invoking Auto with the goal is the user's confirmation of the run. Done when every part of the done condition is covered by some unit's exit evidence.
3. **Classify the doors.** For each unit that acts on a live system, apply the Authority, reversibility, and grants rules in `work/SKILL.md` (**[design-recovery-first](../principles/design-recovery-first.md)**). Reversible two-way doors outside production run; in production they run only under a logged session grant (environment, target scope, allowed change types), passed in the brief. Irreversible one-way doors and all `Teardown` destroys are always user-executed handovers in every environment. Done when every unit carries the authority it runs with.
4. **Dispatch.** Brief each unblocked unit to a fresh subagent on the cheapest tier that can do it; a long-running process goes to the background with a monitor on its exit signal. Open the brief with the goal and where the unit sits in it, then include: the unit itself, `"load the work skill and follow the <name> playbook"`, the exit evidence, the scope, this run's log id for `new --parent` (when in the same project; cross-repo delegates start their own top-level log and return its path; a `Deploy` steps 7–9 execution unit reuses the reviewed preparation delegate's log id instead of running `new --parent` so `run --from-plan` resolves step 5's logged plans with one writer at a time), the unit's authority from step 3, the rule that **the delegate never spawns a reviewer subagent (and runs streams sequentially inline if nested subagents are unavailable)**, and what to hand back: the result, changed paths or artifact revision and preview, criteria and checks run, evidence pointers, its log id/path, and every handover. Do a unit inline only when briefing it costs more than doing it; inline units log directly to this run's log. Done when every unblocked unit is in flight or handed over.
5. **Verify, review, and chain.** A delegate's report is a claim (**[prove-it-works](../principles/prove-it-works.md)**): check its exit evidence against the real diff, artifact, or system, then log the evidence and the delegate's log id. **Do not spawn a reviewer subagent per normal Code unit** — defer Code review to Step 8 (`Close`) or an explicit high-risk phase boundary (such as a foundational scaffold before parallel fan-out). For **`Deploy` preparation** (pre-live safety gate, Deploy step 6), **the orchestrator itself spawns a fresh, non-author read-only reviewer subagent following [`review.md`](review.md) (`Mode: full`)** directly from the orchestrator (never inside the worker subagent), passing the rollout artifact revision, preview, logged plans, criteria, anti-criteria, and delegate log path — never your conclusion. On `Decision: FAIL`, dispatch a fix unit for behavioral/contract/safety `BLOCKER`s and re-run the orchestrator-triggered reviewer in `Mode: delta` (or `Mode: full` if scope widened), capped at 2 follow-up rounds before escalating. Once `Deploy` preparation passes `Decision: PASS`, dispatch the `Deploy` steps 7–9 execution unit on that same reviewed delegate log; if step 7 detects drift and supersedes a plan, that delegate halts before executing and hands back to the orchestrator for a fresh `review.md` `Decision: PASS` before resuming steps 7–9. A failed or partial unit becomes a new unit on the playbook its failure matches, usually Debug or Fix, and the unit it blocked runs again after it: implement, deploy, fix, deploy is this loop. Two failed remedies sharing a premise send you to **[attack-the-premise](../principles/attack-the-premise.md)**; if distinct failures keep chaining past three fix cycles on the same goal without converging, halt and hand the evidence to the user instead of looping indefinitely. A result that changes the goal's shape re-plans the remaining units; log the decision. Done when the unit is accepted on evidence (and `Decision: PASS` for pre-live `Deploy` prep) or replaced by new units.
6. **Hand over and keep moving.** A one-way door, a missing secret, or a decision that changes the deliverable goes to the user: the exact command, target, impact, what cannot come back, and the expected signal, logged as a plan for the user. Units it does not block keep running while it waits. Done when every unit is accepted, in flight, or waiting on a named handover.
7. **Keep the run resumable.** After each accepted unit, log a resume note: units accepted with their evidence, units in flight with their delegates, handovers waiting, and the next units to dispatch. After a compaction, read the latest resume note before dispatching; after a restart, load the work skill again first, since Claude Code hooks end with the process. Done when a fresh agent could continue the run from the log alone.
8. **Close.** When the done condition holds, check it directly. If the goal produced zero code edits, zero prepared rollouts, and zero Ops actions (for example, a sole no-op `Reduce` goal), or falls below `work/SKILL.md`'s significance gate with zero live Ops actions, record `Review: skipped (<reason>, checks green)` instead of running `review.md`. Otherwise **the orchestrator spawns one fresh, non-author read-only reviewer subagent following [`review.md`](review.md) (`Mode: full`)** over the whole goal (step 1 criteria, anti-criteria, every unit's evidence and fresh checks run, the aggregate review surface — all changed paths, prepared rollout artifacts, or completed Ops work-log records — and the work log) and never your conclusion. If behavioral, contract, logic, or security `BLOCKER`s appear at close, dispatch a fix unit (never edit code directly as orchestrator) and re-run the orchestrator-triggered reviewer in `Mode: delta` following `work/SKILL.md`'s PASS-gate loop until `Decision: PASS` (or an explicit user waiver). Run `revert-plan <id>` (which walks nested delegate logs) and close the log with the outcome and any live revert-plan entries. When only handovers remain, stop and report them; the log stays open for the resume. Done on `Decision: PASS`, documented skip, or with every remaining unit waiting on a named handover.

**Reply.** Each turn: the done condition's status, units accepted, in flight, and waiting on a handover (each with its playbook), and the next dispatch. At close: the done condition's evidence, each unit with its playbook and outcome, the review verdict, the log path, and the live revert-plan entries.
