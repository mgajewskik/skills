# Auto

For pursuing one goal the user states up front to completion. Auto wraps a sequence of playbooks: the goal splits into units, each unit runs on the playbook it matches, and you are the orchestrator. Fresh subagents run the units; you plan, brief, verify, and chain (Guard the Context Window). The deliverable is the goal's done condition met on evidence, or the handovers that only the user can pass. The run keeps going without check-ins: the next unit dispatches as soon as the last one is accepted (**[never-block-on-the-human](../principles/never-block-on-the-human.md)**).

1. **Fix the goal.** The goal in one sentence, a binary done condition, constraints and prohibitions, the environments in reach, and any session grant the user has given. Start the log with `--playbook auto` and log each of these as a note. Done when a command or an observation can check the done condition.
2. **Plan the units.** Split the goal into units, each with its playbook, its exit evidence, its scope (files, branch, targets), and the units it blocks. Size a unit so one fresh agent finishes it without compacting. Only units with disjoint scopes run in parallel (**[separate-before-serializing-shared-state](../principles/separate-before-serializing-shared-state.md)**). Log the plan as a note and post it in the reply, then dispatch without waiting: invoking Auto with the goal is the user's confirmation of the run. Done when every part of the done condition is covered by some unit's exit evidence.
3. **Classify the doors.** For each unit that acts on a live system, sort its actions under the Authority and review rules in the work skill. A two-way door is reversible: an exact backup or snapshot of the prior state is captured and verified, a restore command returns it with access you hold, nothing is lost or sent on the way, and a signal confirms the restore (**[design-recovery-first](../principles/design-recovery-first.md)**). Everything else is a one-way door: all Teardown destroys (always user-executed per Teardown step 8, in every environment), data writes, secret rotation, removing access, sending messages, and any change you are unsure you can restore exactly. Two-way doors outside production run; in production they run only under a logged session grant (environment, target scope, allowed change types), passed in the brief. One-way doors are always handovers. Done when every unit carries the authority it runs with.
4. **Dispatch.** Brief each unblocked unit to a fresh subagent on the cheapest tier that can do it; a long-running process goes to the background with a monitor on its exit signal. The brief carries the goal and where the unit sits in it, the unit itself, "load the work skill and follow the <name> playbook", the exit evidence, the scope, this run's log id for the delegate's `new --parent`, the unit's authority from step 3, and what to hand back: the result, evidence pointers, its log id, and every handover. Do a unit inline only when briefing it costs more than doing it. Done when every unblocked unit is in flight or handed over.
5. **Verify and chain.** A delegate's report is a claim (**[prove-it-works](../principles/prove-it-works.md)**): check its exit evidence against the real diff, artifact, or system, then log the evidence and the delegate's log id. A failed or partial unit becomes a new unit on the playbook its failure matches, usually Debug or Fix, and the unit it blocked runs again after it: implement, deploy, fix, deploy is this loop. Two failed remedies sharing a premise send you to **[attack-the-premise](../principles/attack-the-premise.md)**. A result that changes the goal's shape re-plans the remaining units; log the decision. Done when the unit is accepted on evidence or replaced by new units.
6. **Hand over and keep moving.** A one-way door, a missing secret, or a decision that changes the deliverable goes to the user: the exact command, target, impact, what cannot come back, and the expected signal, logged as a plan for the user. Units it does not block keep running while it waits. Done when every unit is accepted, in flight, or waiting on a named handover.
7. **Keep the run resumable.** After each accepted unit, log a resume note: units accepted with their evidence, units in flight with their delegates, handovers waiting, and the next units to dispatch. After a compaction, read the latest resume note before dispatching; after a restart, load the work skill again first, since its hooks end with the process. Done when a fresh agent could continue the run from the log alone.
8. **Close.** When the done condition holds, check it directly, then run a fresh, non-author read-only subagent following [`review.md`](review.md), supplying the brief fields it requires over the whole goal (step 1 criteria, anti-criteria, every unit's evidence, all changed paths, and the work log) and never your conclusion. Fix every `BLOCKER` and re-review until `Decision: PASS` (or an explicit user waiver); any edit after `PASS` voids the verdict. Run `revert-plan <id>` (which walks nested delegate logs) and close the log with the outcome and any live revert-plan entries. When only handovers remain, stop and report them; the log stays open for the resume. Done on `Decision: PASS`, or with every remaining unit waiting on a named handover.

**Reply.** Each turn: the done condition's status, units accepted, in flight, and waiting on a handover (each with its playbook), and the next dispatch. At close: the done condition's evidence, each unit with its playbook and outcome, the review verdict, the log path, and the live revert-plan entries.
