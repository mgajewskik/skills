# Guided

For when the user runs every live command and makes every edit, and you guide. Guided wraps the playbook the task matches (Debug, Live modify, Deploy, Implement, Fix, and the rest): copy the wrapped playbook's numbered step titles into the todolist and carry them out through the handover loop below. The deliverable is the wrapped playbook's deliverable, reached through commands or edits the user ran and output the user pasted back, with a log the user can follow or resume alone. By default you may read local source, run offline local checks that reach no remote system (renders, `validate`, unit tests), and write only the work log and its staging files under `/tmp`; you execute nothing against live systems and edit nothing else, whatever the class or environment. If the user explicitly forbids executing any command at all, run zero local commands and write nothing locally — emit only user-run commands/patches and report the lower verification level (skipping automated checks and subagent review execution).

1. **Fix the contract.** Name the wrapped playbook, environment, target, and shell. Start the log with `--playbook "<wrapped>, guided"` (skip when wrapping read-only `Investigate`/`Review`, or when the user forbids all local commands or writes). For Ops playbooks, the first handover is a read-only check of where the user's commands will land: current context, account, or host, the identity they run as (**[act-through-the-narrowest-identity](../principles/act-through-the-narrowest-identity.md)**), and the `--version` of each tool you will rely on (**[ground-claims-in-the-environment](../principles/ground-claims-in-the-environment.md)**); for offline Code playbooks, confirm repo path, baseline `git status`, and local tool versions instead. Done when that output is pasted back and matches the target.
2. **Hand over one step.** Give the exact command (or minimal patch block for user-applied Code edits) with what it does and why now, its class, the target it hits, the signal you expect, and what to paste back. Independent read-only commands may go together; a change goes alone. Shape commands for pasting: a bounded time window, line count, and field selection, never a full secret or log dump (**[leave-no-residue](../principles/leave-no-residue.md)**). For Ops commands (and user-run Code commands when logging), log each command as `plan --by user` (a change with its revert); a revert you hand over is logged once the user reports running it, as their run with `--reverts <n> --outcome ok|failed|unknown`. Done when the command or patch is logged (when using a log) and handed over.
3. **Order every change.** For Ops changes: snapshot command first (its pasted output becomes the change's revert artifact), then preview/dry run when offered, then the change with its revert command beside it, then the verification command (**[design-recovery-first](../principles/design-recovery-first.md)**, **[prove-it-works](../principles/prove-it-works.md)**). For Code changes: baseline/red test command, exact edit/diff for the user to apply, then local verification command (plus orchestrator-triggered independent review when the change meets `work/SKILL.md`'s significance gate and local execution is permitted). The wrapped playbook's classification stands: name an irreversible step as irreversible and state what cannot come back before handing it over. Done when the snapshot or baseline output is logged before the change is handed over.
4. **Read what comes back.** Ask for the command line together with its output, and check it matches what you handed over (target, flags, identity) before trusting it; a mismatch is a finding, not evidence: log what the user actually ran as their own run (a change with its revert and `--outcome`), note the mismatch, and leave the plan open. Log a match as the user's `run --by user --from-plan <n> --outcome ok|failed|unknown` with a one-line result, save long output to a file and attach it as an artifact, and log each claim it supports or fails as evidence. A message without the requested output is context, not permission to advance. When the log refuses pasted output as a secret, save a redacted copy, delete the unredacted file, and name the line so the user can judge whether to rotate it.
5. **Re-rank and continue** the wrapped playbook from what the output showed, one handover at a time. Two failed remedies sharing a premise send you to **[attack-the-premise](../principles/attack-the-premise.md)**.
6. **Close.** Close the log (when one was used) with the wrapped playbook's outcome. The summary names what the user changed and the revert-plan entries still live. Done when the wrapped playbook's exit evidence holds and the log is closed.

**Reply.** Each turn: the wrapped playbook's current step, what the last output established, and the next command/edit block with what to paste back. At close: the wrapped playbook's reply and the log path (when used).
